# 소리는 어떻게 글이 되고, 글은 소리가 되나

## 1. 소리를 숫자로: 샘플레이트

마이크는 공기의 떨림을 1초에 수천 번 재서 숫자로 바꿉니다. 1초에 재는 횟수가 **샘플레이트**예요.

| 샘플레이트 | 담을 수 있는 최고음 | 어디서 |
|---|---|---|
| 8kHz | 4kHz | 안경 마이크(블루투스 HFP), 옛날 전화 |
| 16kHz | 8kHz | 음성 인식의 표준 입력, 블루투스 광대역(mSBC) |
| 44.1/48kHz | 22~24kHz | 폰 내장 마이크, 음악 |

**나이퀴스트 원리**: 샘플레이트의 절반까지만 기록됩니다. 8kHz 녹음엔 4kHz 위 소리가 아예 없어요.

## 2. 왜 8kHz가 문제인가 (실험으로 확인)

한국어의 **ㅅ, ㅆ, ㅊ, ㅈ, ㅎ** 같은 마찰음·파찰음은 4kHz 위에 중요한 정보가 있어요. 8kHz에선 이게 잘려서 비슷하게 들립니다. 실제로 우리 실험에서:

```
원래 말:  발전기 시동 걸 때 초크는 언제 열어?
16kHz 인식: 발전기 시동 걸 때 초크는 언제 열어?     ← 정확
 8kHz 인식: 발전기 시동 걸 때 쇼크는 언제야?        ← 'ㅊ'이 'ㅅ'으로
```

16문항 평가에서 **문자 오류율(CER)이 0.094(16kHz) → 0.178(8kHz)로 약 2배** 나빠졌어요. 자세한 수치는 [평가 문서](../05-applications/03-evaluation.md).

### 대책 4가지 (Nunchi에 들어 있음)
1. **전처리**: 직류 제거 → 저주파 웅웅거림 제거 → 앞뒤 무음 자르기 → 볼륨 정규화
2. **프롬프트**: LLM에게 "질문은 음성 인식 결과라 비슷한 발음이 틀릴 수 있다. 문서의 비슷한 단어로 이해해라"라고 알려 줌 → '쇼크'를 문서의 '초크'로 이해하고 답함 (실측 확인)
3. **16kHz 경로 쓰기**: Meta DAT의 카메라 스트림 오디오(16kHz, 실험 기능)나 폰 마이크
4. **고유명사 힌트**: `NUNCHI_STT_PROMPT`에 자주 쓰는 단어 적기

> ⚠️ **실험에서 배운 함정 두 가지**
> - 8kHz를 16kHz로 '늘릴' 때 필터 없이 늘리면 고음역에 가짜 소리(이미징)가 생겨 인식이 **더 나빠집니다** ("발전기"→"탈탄기"). Nunchi의 리샘플러는 필터를 거칩니다.
> - 무음 자르기 기준을 "하위 20% 에너지 = 소음"으로 잡으면, 말이 빽빽한 녹음에서 **문장 뒷부분을 잘라 버립니다**. 최댓값 대비 -30dB 기준으로 고쳤어요.

## 3. 소리 → 글자 (STT)

Nunchi는 별도 Whisper 설치 없이 **Gemma 4가 직접 받아쓰기**를 합니다. Ollama의 OpenAI 호환 주소 `/v1/audio/transcriptions` 에 WAV를 보내면 글자가 돌아와요.

```bash
curl http://127.0.0.1:11434/v1/audio/transcriptions -F file=@question.wav -F model=gemma4:e4b -F language=ko
```

- LLM과 같은 모델(e4b)로 받아쓰면 **모델 교체 대기가 없어** 빠릅니다(실측 STT 중앙값 0.2초 안팎).
- whisper.cpp 서버도 연결할 수 있어요 (`NUNCHI_STT_BACKEND=whispercpp`).

## 4. 글자 → 소리 (TTS)

| 방식 | 어디서 | 장점 | 단점 |
|---|---|---|---|
| **폰 TTS** (권장) | iOS AVSpeechSynthesizer / Android TextToSpeech | 가장 빠름, 오프라인 | 기기마다 목소리 다름 |
| Ollama `lfm3-audio:2b` | 허브 | 한국어 목소리(female-korean/male-korean), 크로스플랫폼 | 문장마다 0.3~1초, 가끔 긴 문장 잘림 |
| macOS `say` | 맥 허브 | 설치 불필요, Yuna 목소리 | 맥 전용 |

### 문장 단위 스트리밍 — 기다림을 줄이는 핵심
답 전체를 기다리지 않고, LLM이 **첫 문장을 완성하는 순간** 읽기 시작합니다. 허브가 SSE로 `sentence` 이벤트를 보내고, 폰이 바로 읽어요.

```
0.0s 질문 끝 → 0.2s 인식 → 0.3s 검색 → 0.5s 첫 문장 완성 → 🔊 읽기 시작
                                         (나머지 문장은 읽는 동안 생성)
```

## 5. 귀로 듣는 답을 위한 정리

LLM은 마크다운(`**굵게**`, `- 목록`)을 좋아하지만 TTS는 그걸 "별표 별표"라고 읽거나 멈춥니다. Nunchi는 읽기 전에 마크다운·이모지·인용번호([1])를 걷어내고, 줄 끝에 마침표를 붙여 자연스럽게 쉬게 해요. → [음성 UX 원칙](../02-concepts/05-voice-ux.md)
