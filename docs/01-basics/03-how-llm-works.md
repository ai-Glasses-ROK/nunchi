## 1. 다음 글자 맞히기 기계

LLM(대형 언어 모델)이 하는 일은 단 하나, **"지금까지의 글 다음에 올 토큰은 무엇일까?"** 를 맞히는 것입니다.

```
입력:  캠핑장 체크아웃은 오전
예측:  11(42%)  10(31%)  9(8%) …  → '11' 선택
입력:  캠핑장 체크아웃은 오전 11
예측:  시(97%) …                  → '시' 선택
```

이걸 수백 번 반복하면 문장이 됩니다. 그래서 답이 **한 글자씩 흘러나오고**(스트리밍), 첫 글자가 나오는 시간(**첫 토큰 지연**)과 전체 시간이 따로 있어요.

## 2. 토큰

모델은 글자를 '토큰'으로 잘라 셉니다. 한국어는 대략 1토큰 ≈ 1~2글자.

- 속도: "초당 토큰 수(tok/s)". M5 Pro에서 gemma4:e2b-mlx는 짧은 답 기준 초당 100토큰 이상 나왔어요(실측 21토큰에 0.16초).
- 길이: 컨텍스트 창(예: 8,192토큰)을 넘으면 앞부분을 못 봅니다. 그래서 RAG는 **필요한 조각만** 골라 넣어요.

## 3. 파라미터와 메모리

파라미터는 모델 안 숫자의 개수입니다. 메모리는 대략 이렇게 계산해요.

```
필요 메모리 ≈ 파라미터 수 × 숫자 하나의 크기 + 여유(컨텍스트·엔진)
  예) 4B 모델 × 4bit(0.5바이트) ≈ 2GB + 여유 1~2GB
  예) 4B 모델 × 16bit(2바이트) ≈ 8GB + 여유
```

| 모델 | 크기(Ollama 표기) | 특징 |
|---|---|---|
| gemma4:e2b | 4.6~7.5GB | 가볍고 빠름. 폰급 |
| gemma4:e4b | 6.6~9.5GB | 이 레포의 기본. 글·사진·소리 모두 |
| gemma4:12b / 26b / 31b | 8~20GB | 더 똑똑, 더 무거움 |
| gpt-oss:20b | 13GB | 텍스트 전용, 추론(사고) 강함 |

> "E2B"의 E는 effective(실효). 실제 파일엔 시각·음성 부품까지 들어 있어 표기 파라미터보다 큽니다(`ollama show`로 5.2B로 표시).

## 4. 양자화 — 모델 다이어트

원래 16bit인 숫자를 8bit·4bit로 줄이면 크기가 1/2~1/4이 됩니다. 정확도는 조금 떨어지지만 체감은 작아요. Ollama 태그의 `q4_K_M`, `qat`, `nvfp4`, `mxfp8` 같은 꼬리표가 양자화 방식입니다.

- **qat**: 양자화를 고려해 학습한 버전(같은 4bit라도 품질이 좋음)
- **mlx / nvfp4**: 애플 실리콘 MLX 엔진용

## 5. 사고(thinking) 모드

일부 모델은 답하기 전에 속으로 풀이를 길게 씁니다.
- 수학·논리 문제: 정확도가 크게 오름
- 음성 비서: 답이 늦어짐 → **Nunchi는 기본으로 끔** (`NUNCHI_THINK=false`)

수능 수학에서 사고 모드가 얼마나 차이를 만드는지는 [평가 문서](../05-applications/03-evaluation.md)에서 실측했어요.

## 6. 환각과 RAG

LLM은 "모른다"보다 "그럴듯한 말"을 만들도록 학습돼 있어서, 모르는 걸 지어낼 수 있어요(환각). 해결책이 **RAG**: 답하기 전에 내 문서에서 근거를 찾아 같이 주는 것. → [RAG는 어떻게 내 문서를 아나](04-how-rag-works.md)

## 7. 이 프로젝트의 기본값이 그런 이유

| 설정 | 값 | 이유 |
|---|---|---|
| 모델 | gemma4:e4b (맥은 e4b-mlx 자동 선택) | 한 모델로 글·사진·**소리 인식**까지 → 모델 교체 대기 없음 |
| 온도 | 0.3 | 비서는 일관성이 중요 |
| 최대 토큰 | 384 | 음성 답은 짧아야 함 |
| 사고 모드 | 끔 | 지연 최소화 |
| keep_alive | 30분 | 모델을 메모리에 붙잡아 두어 첫 질문도 빠르게 |
